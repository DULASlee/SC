# Agnes 3.0 Flash 缓存命中第二轮取证 + 「能不能自己在 IDE 里微调」的层次判定

- 日期：2026-09-20（下午 16:1x–17:0x 复测；接续同日 v4 报告与 ADR-0005）
- 对象：`agnes/agnes-3.0-flash` 前缀缓存行为、成本结构、整改杠杆归属
- 取证工具：`docs/ai-workspace/tools/agnes-cache-probe/`（`cache_probe.py` 在线探针、`miss_triage.py` 离线判读）
- 关联：`docs/reports/2026-09-20-agnes-3.0-flash-slow-diagnosis.md`（v4）、
  `docs/architecture/adr/ADR-0005-Compaction-Threshold-Keep-0.2-Over-0.7.md`

## 〇、四条结论

1. **命中率不发生在模型这一层。** 前缀缓存的键是 token 序列前缀、值是 GPU 里的 KV，命中与否只取决于
   「前缀是否逐字相同 + 哪台实例还留着它」。微调改权重，权重不参与这条判定的任何一步；
   且 agnes-3.0-flash 是闭源推理 API——官方文档全集（`wiki.agnes-ai.com/llms.txt`，26 页）只有
   chat/completions、responses、messages 三个推理端点与定价/FAQ，**没有 fine-tuning 产品、没有权重下载**。
   ⇒ IDE 里既无权重可训，也无缓存可控。
2. **"命中偏低"的真实成因是两层叠加，且都不在客户端**：① 端点缓存是**严格链式 + 256 分块**的
   （命中步 `cached(k)≈prompt(k-1)`，失配中位 −0.55%），所以它只在"上一条请求的整段 prompt 还在
   同一台实例里"时成立；② 端点前置 Cloudflare、源站多实例，客户端**无法**把请求钉到同一实例。
   同一天下午复测，`cached_tokens` 从上午的 59% 上报命中变成 **5 轮探针约 40 次请求无一次非 0**。
3. **下午的 0 命中不能全算缓存故障**：1.8K token 的请求也能用 54.8s 甚至 162s（21 tok/s）——
   这个量级的抖动只能来自排队/争用。⇒ 当前 agnes 的第一问题是**服务级排队不可预测**，
   缓存不稳是第二问题；两者都要求"换端点"而不是"调自己"。
4. **本轮找到一个真正可控的新变量：会话龄期。** 同一会话内按"距上次前缀改写的时间"分层，
   真 miss 率 <10min 为 11–20%、>60min 为 **45%**，会话最初 13 步（无 prune）为 **0%**。
   ⇒ 对症动作是**及时新开会话**；而"保持前缀稳定"这条 v4 建议的收益被高估（见第一节第 3 条）。

## 一、机制证据（离线，会话 d503d810，100 次请求，零成本）

### 1. 端点缓存是「严格前缀链式 + 256 分块」

| 判据 | 实测 | 结论 |
|---|---|---|
| 命中步 `cached(k)` vs 上一步 `prompt(k-1)` 失配率 | n=58，中位 **−0.55%**（均值 −5.5%） | 命中 = **上一条请求整段 prompt** 被复用 |
| `cacheRead` 取值 | **100/100 步是 256 的整数倍** | 分块缓存（block size 256） |
| miss 步 `cacheRead` 取值 | gen1：`0 / 6,400 / 7,680 / 7,936`；gen2：`2,304 / 3,584 / 6,400 / 7,936` | 分歧点**不固定**，见第 3 条 |

工具定义块实测 28,496 字符 ≈ **7.1K–9.2K token**（÷4 与 ÷3.13 两口径）——与 miss 步最常见的
`6,400/7,936` 同量级 ⇒ v4 的「miss 时只剩共享系统+工具块命中」在数值上成立。
但 gen2 出现 `2,304/3,584`（**小于工具块**）：同一会话的同一个工具块不可能"一半命中"由客户端解释，
只能是**不同实例上残留的条目长度不同** ⇒ 后端状态类根因，客户端无处着力。

### 2. 状态慢变（不是每请求轮询）

```
游程序列: M2 h1 M1 h9 M4 h7 M1 h4 M6 h7 M3 h1 M2 h5 M6 h1 M5 h1 M1 h1 M1 h1 M1 h15 M3 h1 M2 h2 M3 h3 M1 h1
miss 游程均值 2.69 / i.i.d. 期望 1.86 = 1.45×
hit  游程均值 4.64 / i.i.d. 期望 0.54 = 8.62×
相邻步翻转率 26%（i.i.d. 期望 46%）
```

慢变 ⇒ 存在"实例级状态"，理论上钉住实例就能稳定命中——但见第三节：钉不住。

### 3. 真 miss 的主导变量是**会话龄期**，不是规模、不是改写、不是重试

先建立双判据（见第四节），再逐一对齐：

| 候选因 | 分组 | 按 `cacheRead` 判 | 按墙钟双判据判（真 miss） |
|---|---|---|---|
| 距上次前缀改写 <1min | n=5 | 80% | **20%** |
| 距上次前缀改写 1–10min | n=18 | 28% | **11%** |
| 距上次前缀改写 10–60min | n=10 | 20% | **20%** |
| 距上次前缀改写 >60min | n=67 | 45% | **45%** |
| header 世代 gen0（首 13 步，无 prune） | n=13 | 23% | **0%** |
| header 世代 gen1（71 步） | n=71 | 41% | **37%** |
| header 世代 gen2（16 步） | n=16 | 56% | **56%** |
| prompt 规模（gen1 内 161K–438K） | n=71 | — | **r = +0.039（无关）** |
| miss 段起点前 180s 内有 retry/attempt | 1/13 = 8% | — | 命中步基线 12%（反向） |

⇒ 与规模的无关性在**同一 header 世代内**被独立复现（支持 ADR-0005 证据 1）；
真正单调上升的是**会话已运行时长**：越到后面，链越容易失效。这既不是"我们改了前缀"，也不是"prompt 太大"，
而是后端条目随时间被淘汰/漂走。

### 4. 分类结果（真 miss = 计量低 **且** 墙钟不低于全量重算下界）

| 分类 | 步数 | TTFT 中位 | 合计 | 占比 |
|---|---|---|---|---|
| 真命中且上报 | 54 | 22.2s | 1,421s | 20.6% |
| 命中但 `cached_tokens` 未上报 | 6 | 22.6s | 132s | 1.9% |
| **真 miss（整段重算）** | **35** | **120.8s** | **4,551s** | **66.0%** |
| 命中但慢（排队离群） | 5 | 95.7s | 793s | 11.5% |

ADR-0005 的「41% miss」是**上界**，按墙钟修正为 **35%**；结论方向不变（其收益估算偏保守 6pt）。

## 二、同日复测：端点行为在一天内从 59% 命中劣化到 0% 上报命中

同一台机器、同一 key、同一协议（`cache_probe.py`，22 次请求，25K/34K/110K payload，
同连接与跨连接，间隔 15–45s）：

| 项 | agnes-3.0-flash | MiniMax-M3（阳性对照） |
|---|---|---|
| 25K 句尾盐·同连接三次复测（间隔 20s/12s） | `cached=0`；墙钟 **58.47s → 53.51s → 3.54s**（16×） | `cache_read=24,470`，2.1s → 1.3s（**完整命中**） |
| 11K 句尾盐·同连接三次复测（间隔 15s） | `cached=0`；墙钟 **6.26s → 1.60s → 16.76s**（10×） | — |
| 句首盐（首 token 即分歧） | `cached=0`；38.62s → 23.17s | — |
| 跨连接复测 | `cached=0`；44.40s → 3.88s | — |
| 110K payload（两次独立运行） | `cached=0`；墙钟序列 **19.06s → 134.64s → >300s 超时**，另一次 **214.1s → 30.8s** | — |
| **1.8K 极小 payload（同连接三次，间隔 10s）** | `cached=0`；墙钟 **13.34s → 54.82s → 16.55s** | — |
| **1.8K 另一 arm** | `cached=0`；**6.81s → 161.96s（=21 tok/s）** | — |
| `cached_tokens` 上报 | **约 40 次请求无一次非 0**（5 轮独立运行） | 正常上报 |

三点必须写清：

1. **请求构造没变，命中率变没了**（上午 59% → 下午 0%）⇒ 命中率是端点侧慢变量，与我们的 prompt 无关。
2. **但不能据此断言"端点缓存坏了"**：1.8K token 的请求也能用 54.8s 与 162s（21 tok/s）——
   这个量级的抖动与缓存机制无关，只能是排队/争用。⇒ 在当前负载状态下，`cached_tokens` 与单次墙钟
   **都**不足以判定缓存机制；本轮唯一可信的是**相对结论**。
3. **相对结论不受抖动影响**：同机、同网、同一时刻、同一协议下 MiniMax-M3 用 2.1s/1.3s 完成 25K 请求并
   如实上报 `cache_read=24,470`，agnes 用 44–214s 且报 0 ⇒ **相差 15–100 倍**，选型结论稳固。
   而"41%/59% miss"这一机制结论仍以上午那次**真实 100 步会话**（计量与墙钟互证，见第四节）为准，
   不依赖合成探针。

### 方法论教训：先用极小 payload 定"排队税"基线，再测缓存

同一探针用 1,764 token 的极小 payload 复跑，结果：

| 同一 1.8K payload（同连接） | 6.81s | 8.79s | 13.34s | 16.55s | 20.93s | 26.03s | 54.39s | 54.82s | **161.96s** |
|---|---|---|---|---|---|---|---|---|---|
| 折算 tok/s | 260 | 201 | 132 | 107 | 84 | 68 | 32 | 32 | **21** |

1.8K token 无论如何不可能需要 162s 预填充 ⇒ **当前 agnes 的主导成本是排队/争用，与 prompt 规模、缓存命中都不成比例。**
推论两条：① 今天不能用合成探针测"命中率"（信噪比不足，测到的全是排队），机制判读以真实会话为准；
② 每步固定税不只是上午测到的 21.9s 中位，而是**量级 7–162s、方差极大**——
这把"减步数 / 换端点"的优先级进一步抬高，把"追命中率"的优先级压低。
（首次跑探针时我漏了这条基线 arm，导致差点把排队误判成"缓存完全失效"。）

**同一探针第二次运行（16:4x）复现并加重**：1.7K payload 的复测为 70.9s / 10.4s / 57.9s，
且 5 次请求中有 2 次 warm 直接 `RemoteDisconnected('Remote end closed connection without response')`
⇒ 端点现在**同时**存在排队、连接重置与 `cached_tokens` 恒 0 三个症状。
工具已把该基线固化为 `Q-queue` arm（排在所有缓存 arm 之前），并要求先读它再读 hit/miss。

**17:0x 第三次复跑（工具改造后的定点校验）**：一个 **644 token** 的请求 warm 用去 **60.28s（11 tok/s）**。
644 token 连一次正常排队都不该用 60 秒 ⇒ 结论钉死：**当前 agnes 端点的第一约束是排队/争用，不是缓存**。
上午真实会话里"每步 21.9–122s"的 TTFT，现在用 644 token 就能重现——这与 prompt 体积、与命中率、
与模型权重都无关。追"缓存命中率"在今天已不是正确的战场。

## 三、为什么客户端拿不到"钉住后端"这个把手（ADR-0005 由推测升级为实测）

```
Server: cloudflare
CF-RAY: a3df5870dc8197d3-CZX    ← 同一 TCP 连接 3 次请求，尾部节点标识恒为 97d3
CF-RAY: a3df5c0b6cbe4e94-CZX    ← 换一条连接即变 4e94
Resolve-DnsName api.agnes-ai.cn → 单条 A 记录 36.153.95.129（anycast）
```

- 我们唯一能钉住的是 **Cloudflare 边缘节点**；`api.agnes-ai.cn` 只解析出 1 个 IP，**换 IP/hosts 固定不存在**；
- 同连接、同 payload、间隔 45s 仍 `cached=0` ⇒ **边缘→源站的实例分发不受客户端控制**；
- `user` / `prompt_cache_key` 字段实测对命中无影响（v4），且 agnes 的 Chat Completions 请求字段表
  （官方文档）里**没有任何缓存/亲和相关字段**可传。

⇒ 结论与 ADR-0005 一致：缓存亲和是**厂商侧**必须解决的问题（需其提供账号级粘性或 origin 实例标识头）。

## 四、判读口径（本轮新增，必须长期遵守）

**`usage.prompt_tokens_details.cached_tokens` 不可单独作判据。**
本轮实测：112,085 token 的请求 30.8s 完成（3,639 tok/s，快于其自身冷启动回归 2,244 tok/s 的 1.6 倍）
却报 `cached=0`；同 payload 的另一次请求用 214.1s 同样报 0。方向与 v1–v3 的误判**相反**
（v1–v3 是"有缓存但报 0"被误判为"无缓存"，本轮是"报 0 且确实慢"与"报 0 但很快"混在一起）。

固定口径：**miss 当且仅当 `cacheRead < 20K` 且 `TTFT ≥ max(30s, 0.5 × prompt/2244 tok/s)`**。
两口径差值（本会话 6 步）即"命中未上报"量，需作为独立指标跟踪。

## 五、成本三项分解（100 步，实测 TTFT 合计 6,896s）

`miss_triage.py` 输出（模型合计 7,322s，对实测 6,896s 高估 6%，份额比绝对值更有意义）：

| 项 | 量 | 占比 | 谁能动它 |
|---|---|---|---|
| 每步固定税 100 × 26.9s（干净命中步子集为 22.2s，ADR 口径 21.9s） | 2,686s | 36.8% | **只有减步数或换端点**。与 prompt 规模无关（`r(uncached, TTFT) = −0.076`；uncached<1K 桶 22.5s vs uncached>30K 桶 30.2s）。**微调权重同样动不了它**——它发生在排队/调度层 |
| 35 步真 miss 整段重算 | 4,175s | 57.2% | 只能缩小 prompt（命中率不可控） |
| 59 步命中增量重算（uncached 中位 6.2K） | 431s | 5.9% | 工具输出体积 |

| 另有解码 122 tok/s、平均 469 tok/步 ≈ 8.5s/步 | — | — | 端点属性（官方榜单输出速度 252.7 tok/s） |

（注：第一节 2×2 表里的"真 miss 合计 4,551s / 66.0%"是按**实测 TTFT 求和**、以 6,896s 为分母；
本表 4,175s 是按 **prefill 下界** `prompt/2,244` 估算、以模型和 7,322s 为分母，用于跨档位比较。
模型对实测高估 6%，用份额而非绝对值下结论。）

**收益上界**：把命中率修到 100% 至多省 4,606s（−63%）；剩下的每步固定税一分都省不掉。
**MiniMax 同协议 warm 2.1s ⇒ 同一 100 步任务的固定税约 210s，差约 11×。**

## 六、参数寻优：压缩阈值这条杠杆已经见底

沿用 ADR-0005 的校准公式（对 0.8/0.7/0.5/0.3 行复现误差 ≤5%；`0.2/32768` 复现 3,260s vs ADR 3,296s）：

| thresholdRatio / retainTokens | 真实峰值 | 压缩次数/100步 | 100 步合计 | vs 当前 0.2 |
|---|---|---|---|---|
| **0.20 / 32,768（当前）** | 134,217 | 4.6 | **3,260s** | — |
| 0.06 / 4,096 | 40,265 | 12.1 | 2,214s | −32% |
| 0.05 / 3,072 | 33,554 | 14.3 | 2,166s | −34% |
| 0.04 / 3,072 | 26,843 | 18.5 | 2,160s | −34%（每 5 步压一次，逐字保留仅 3,932 tok） |

**不建议采纳，两条理由：**
1. 收益 100% 来自"给不可控 miss 买保险"——敏感性检验：miss 率 41%→20%→5%→0% 时，该收益
   −29%→−16%→−5%→**−0.8%**。也就是说这些档位只是在逼近 2,220s 的固定税地板，
   而代价是每 5–8 步一次压缩、逐字保留跌到 ~4K token（正确性风险，模型看不见）。
2. 第一节第 3 条已证明真 miss 的主导变量是**会话龄期**而非 prompt 规模 ⇒ 继续下调阈值治的是错的病。

⇒ **维持 ADR-0005 的 0.2 不变**；把 `0.05–0.08` 记为"端点持续 0 命中时的应急档"，不默认启用。

## 七、正面回答：IDE 里到底能"微调"什么

| 层 | 决定什么 | 与命中率的因果位置 | 我们在 IDE 里能否改 |
|---|---|---|---|
| L0 模型权重 | 给定 token 序列算出的 KV 数值 | **无关**（命中判定只比前缀是否逐字相同，KV 值不参与判定） | **否**：闭源、无权重、无训练 API |
| L1 请求构造 | 前缀是否逐字稳定；每步有多少 token 必须重算 | 强相关（链式 + 256 分块已实测） | **能**：工具输出体积、易变内容只追加末尾、检索优先 |
| L2 网关/路由 | 请求落到哪台实例 | **决定性**（本轮 0% 命中发生在此层，Cloudflare 之后） | **否**：单 anycast IP，无亲和字段可传 |
| L3 实例缓存策略 | 容量/淘汰/TTL/异步写 | 决定性（真 miss 随会话龄期升到 45% 即此类） | **否** |

反直觉但必须说清：**真去微调并另起部署，命中率只会更差**——新部署 KV 池全冷、前缀条目需重建，
而判定机制一个字没变；我们唯一能确定改变的是"多花一次全量预填充"。

把"微调"落到能做的三档（按实测收益排序）：

1. **换端点（最大，100% 可控）**：`settings.yaml` + `cordis.patch.yml` 里把长任务/大上下文默认路由到
   MiniMax-M3（本轮阳性对照实测：25K 请求 warm 2.1s / probe 1.3s 且 `cache_read=24,470` 完整命中，
   agnes 同协议 44–214s 且报 0 ⇒ **每步固定税约低 11 倍**）；doubao 的"38 万 tok/步 TTFT 4.6s"是 v4 在
   DSH 内的观测，本轮裸 API 复现失败（`UnsupportedModel: agent plan`），**换端点前需在 DSH 形态下复核**。
   agnes 只留小上下文任务。**这就是"在 IDE 里微调"的正解：调配置层的路由，不是调模型权重。**
2. **控会话龄期（本轮新发现，0 成本）**：真 miss 从会话前 60 分钟的 11–20% 升到之后的 45%。
   动作：长任务切分为多会话（每会话 ≤60 分钟 / ≤40 步），别指望一个会话跑完 100 步。
3. **减步数（撬动 36.8% 每步固定税的唯一手段）**：步数减半≈总时长减半。
   手段已就绪：`jqkj-search`（413,998→8,500 字符）、批量工具调用、探索性检索委派 subagent、TASK-032 规则卡。

若目标是"让模型更贴合本项目"：本会话 92.8% 的 prompt 是工具结果，权重再贴合也不会少读文件；
对症做法是工具输出纪律（TASK-032），当天生效、成本近零，与训练无关。
