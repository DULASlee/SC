## 一、根因重述：不是提示词太长，是检索不够精确

之前的整改（下调压缩阈值）只是**止血**——它限制最坏情况下的 prompt 体积，但没有改变"每步都要塞进 5,000-16,000 字符"的事实。真正的根因是：

> **智能体缺少精确的文档/代码检索手段，只能退化为「整文件读入 + 目录递归列举」。**

### 证据 1：那 4 次 `grep` 的实际结果（会话 d503d810）

| 调用 | 结果 |
|---|---|
| `{"pattern":"TASK-002","path":"F:\\JQKJ"}` | 649 字符（有效） |
| `{"pattern":"MQTT.*(断开\|点丢失\|30s)\|...\|30\\s?s.*MQTT"}` | **16 字符 = 零命中** |
| `{"pattern":"灯号\|cloud\|聚合服务\|uplink\|MQTT 上报"}` | 128 字符 |
| `{"pattern":"\\.NET.*云\|BFF\|IoTPlatform.*云端\|..."}` | 2,720 字符 |

### 证据 2：零命中的真实原因是「提问用词 ≠ 文档用词」

对语料做词元存在性核查：

| 词元 | 命中章节数 |
|---|---|
| `MQTT` | 717 |
| `断开` | 32 |
| **`云端聚合`** | **0** |
| **`点丢失`** | **0** |
| `丢失` | 44 |

**纯正则检索永远跨不过这道鸿沟，而且失败时不给任何可行动信息**——agent 拿到 16 字符的"零命中"后，唯一能做的就是逐个读文件。这就是 126 次 `read` 的机制。

### 证据 3：读取量的分桶（基线）

| 用途 | 次数 | 字符 |
|---|---|---|
| **文档类**（`docs/**`、`*.md`） | **47** | **413,998** |
| 源码类（`src/**`） | 39 | 324,872 |
| 工作区外（`F:\maiyata`、`~/.claude`） | 17 | 111,904 |
| 其他 | 23 | 100,808 |
| 合计 | 126 | 951,582 |

外加 4 条 `Get-ChildItem -Recurse` 目录树，各被截断在 50,000 字符。

## 二、交付的工具

`jqkj-search`：Python 标准库实现，SQLite **FTS5(trigram)** 索引，四个子命令。

| 子命令 | 作用 | 替代什么 |
|---|---|---|
| `doc <词元...>` | 概念级文档检索：BM25 + 密度排序，返回**章节**（标题路径 + 行号 + 片段） | 整篇文档读取 |
| `sym <名字> [--refs]` | 符号定义 / 引用定位，返回 `file:line` | 为找一个类而读多个文件 |
| `outline <文件>` | 文档标题树 / 代码符号表（带行号） | "先读一遍看看结构" |
| `find <glob>` | 路径检索，只回计数 + 少量路径 | `Get-ChildItem -Recurse` 目录树 |
| `index` | 增量重建索引（按 mtime+size） | — |

索引规模：**265 文件 / 2,026 文档章节 / 813 符号，建索引 1.5 秒**。

## 三、实测效果

| 查询 | 本工具 | 原方式 | 压缩比 |
|---|---|---|---|
| `doc "MQTT 断开"` | **1,729 字符**；第 1 条即 `docs/architecture/mqtt-topics.md:69-75`「5.2 断线续传」 | 正则零命中 → 整文件读取 | — |
| `sym CollectorEngine` | **157 字符**（`Core/CollectorEngine.cs:12 class`） | 读 `CollectorEngine.cs`（5,988 字符） | 38× |
| `sym MqttPublisher --refs` | **~400 字符**（1 定义 + 3 引用，带行号） | 读 2 个文件（~8,000 字符） | 20× |
| `find "**/*.csproj"` | **677 字符**（12 项） | `Get-ChildItem -Recurse` 50,000 字符 | 74× |
| **文档检索子任务整体** | 约 5 次 `doc` ≈ **8,500 字符** | **413,998 字符**（47 次 read） | **48.7×** |

按 v4 报告的换算（3.1 字符/token），仅文档检索一项即可让每步 prompt 少 **13 万 token**。

## 四、设计决策与踩过的坑（可复用）

1. **trigram 分词器不支持 <3 字符的词**——CJK 双字词（"断开"）必须靠 LIKE 兜底。
   故实现为混合检索：≥3 字符词元走 FTS5 取候选，再用 LIKE 强制全部词元命中。
2. **零命中要给出可行动信息**——词元不存在时提示语料中真实存在的 2 字片段
   （`点丢失` → `丢失(44)`）。这是把"搜不到"从死胡同变成下一步的关键。
3. **密度排序优于命中计数**——否则 468 行的巨型计划文档会霸榜；改为 `命中数/千字符`。
4. **内容去重 + 排除 `.harness/worktrees/`**——实测 worktrees 是同一仓库在不同任务态下的整份副本，
   索引它会让同一文档以 3-4 条重复命中（TASK-008/009/010 各一份）并污染排序。
5. **强制 UTF-8 输出**——Windows 控制台默认 GBK 会让中文乱码（本次多个命令都出现过）。
6. **`.cmd` 包装器必须纯 ASCII**——中文注释会被 GBK 控制台拆成乱码命令并当作指令执行
   （实测 stderr 出现 `'MQTT' is not recognized as an internal or external command`）。
   已重写为 0 个非 ASCII 字节，退出码 0、无 stderr 噪声。

## 五、如何采纳

0. **落位说明（治理）**：工具最初放在 `.tools/search/`，但 `.tools/` 已被 `.gitignore` 覆盖（该目录用于存放
   dnSpy/Ghidra 等大体积二进制），会导致工具**不进版本库、其他 agent 取不到**；且铁律 14 要求脚本存放于
   `docs/` 对应子目录。故迁至 **`docs/ai-workspace/tools/jqkj-search/`**（与 `skills/`/`hooks/`/`mcp/`/`prompts/`
   同级，符合原则 6「AI 配置唯一源在 docs/ai-workspace/」），仅把可重建的索引留在 `.tools/search/index.db`。
   *（`docs/ai-workspace/tools/` 是本次新增的子目录类别，请架构师在评审时确认或改派。）*

1. **规则层**：把"检索优先"写进铁律（草案见 splan 的 TASK-032）：
   - 定位文件用 `jqkj-search sym` / `doc` / `find`，禁止用整文件读取代替检索；
   - 读文件前先 `outline`，读取必须带 `offset`/`limit`；
   - 禁止目录递归列举入上下文；
   - 跨工作区路径读取需显式授权。
2. **验证口径**：后续同类任务的 `read` 调用占比应从 **74.6% 降到 <20%**，
   文档检索子任务的字符量应从 41 万降到 1 万以内。
3. **后续扩展**（按需）：
   - 索引扩展 `.yaml`/`.json`/`.proto` 等配置文本；
   - 用 tree-sitter 替换正则符号抽取（当前 `sym` 对泛型/表达式体成员可能漏检）；
   - 若"用词鸿沟"仍是瓶颈，再加 embedding 语义检索（当前靠零命中提示缓解）。
