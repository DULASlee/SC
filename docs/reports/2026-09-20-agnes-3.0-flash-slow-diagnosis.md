## 〇、更正声明（v4）

v1~v3 报告中"agnes 端点 prompt 缓存完全不生效"的结论**错误，现予更正**：

- **错因**：判据用的是"相邻两次相同 payload 的 A/B"，间隔仅 0.4~3s；而 agnes 的缓存是**异步写入**的，写入完成前第二次请求必然 miss，于是被误判为"无缓存"。
- **正确结论**：缓存**生效且收益巨大**。间隔 10s 以上复测即命中：`prompt_tokens=25274, cached_tokens=25088`，耗时 2.66s → 0.65s。`user` / `prompt_cache_key` 字段对命中无影响（按内容前缀缓存）。
- **判读规则（已沉淀 lessons）**：验证异步缓存必须间隔 ≥10s 复测，并核对 `usage.prompt_tokens_details.cached_tokens`。

## 一、直接回答"为什么每步 30 万 token"

30 万是**单请求真实值**（逐请求重算，非累计值误读）：`median=328,795 / mean=300,508 / max=438,042`，与端点返回的 `prompt_tokens` 一致。

但它**不是**"深入提示词"——系统提示仅 1,313 token、26 个工具定义约 7K，合计 8~14K。构成如下（transcript 877 事件统计）：

> **v4.1 更正**：下表原用 `json.dumps(事件)` 长度，被 JSON 转义虚高约 2.6 倍。按**消息正文文本**重算如下（详见 `docs/reports/2026-09-20-tool-result-context-bloat-analysis.md`）：

| 内容类型 | 条数 | 正文总字符 | 占比 |
|---|---|---|---|
| **tool/result（文件内容、命令输出、检索命中）** | **230** | **1,274,982** | **92.8%** |
| assistant/message | 100 | 66,663（均 666） | 4.9% |
| **user/message（人类输入）** | **17** | **27,496** | **2.0%** |
| system/message | 1 | 5,231 | 0.4% |

（230 = **189 次真实工具调用 + 41 条修剪器重写副本**；其中 126 次是 `read`，占工具输出 74.6%。）

单条工具结果最大 **50,000 字符**（pwsh 目录递归列举，被工具上限截断），其后为 49,976 / 49,910 / 48,518（整文件读取）。8 条 >20K 字符的结果合计 321,564 字符 = 全部工具输出的 25.2%。（原记 "126,279 字符" 为 JSON 转义后的虚高值，已更正。）

**结论：prompt 是被工具结果堆大的，不是被系统提示词堆大的。** 人类输入仅占 2.0%，assistant 正文平均 666 字符。

## 二、真正的性能杀手：34% 的步整段缓存未命中

| 指标 | 数值 |
|---|---|
| 未缓存量 A 中位数 / 均值 | 31,446 / 128,612 |
| 全量未命中步（A>200K） | **34/100（34%）** |
| 近全命中步（A<20K） | 43/100（43%） |
| 命中步 TTFT 中位数 | **21.9s** |
| 未命中步 TTFT 中位数 | **122.4s**（最大 176s） |
| 未缓存预填充吞吐 | **≈2.2K tok/s**（317K 未缓存 → 151s；369K → 163s） |
| TTFT 合计 / 占比 | **6,896s（1.92h）**，占 LLM 耗时 87% |
| 反事实（若全部命中，按中位 21.9s） | ≈2,191s（0.61h） |

典型对照（同一会话相邻步）：

```
6/1  A=314,732  cached=7,936   prompt=322,668  TTFT  95.5s
7/1  A=317,633  cached=7,936   TTFT 151.0s
7/5  A=330,028  cached=0       TTFT 100.9s
7/6  A=4,790    cached=325,376 TTFT  18.4s   ← 命中，33 万 token 仅 18.4s
```

**未命中成因排查（均已排除）**：

| 假设 | 检验结果 |
|---|---|
| 步间隔过长致 TTL 过期 | 未命中步的前置间隔中位数 **0.0s**（命中步 0.1s）——无差别 |
| compaction/prune 改写前缀 | 未命中步前一窗内有 prune 的仅 **1/34（3%）**；命中步 0/42 |
| todo/write 改写前缀 | 9% vs 命中步 17%——反向 |
| inbox/spliced 改写前缀 | 18% vs 命中步 10%——不显著 |
| 端点缓存不可用 | **剩余解释**：miss 期间仅开头 ~6.4K（工具块）命中、对话主体整段失效，属端点侧行为 |

## 三、次要因素

1. **端点稳定性**：transcript 5 次 `llm/retry`（2×HTTP 500、2×stream idle timeout、1×流中断），每次重试重付全额预填充。
2. **排队波动**：即使 OpenCode 小请求也出现 61s / 138.6s 离群；本会话单步 TTFT 最大 431.2s。
3. **解码速率** 47 tok/s（官方榜 252.7）。

## 四、为什么 OpenCode 里"表现优秀"

| 客户端 | 单请求输入 | 延迟 |
|---|---|---|
| OpenCode（opencode.db，245 条 agnes 消息） | 0.6K~33K tok | 多数 0.5~14s |
| DSH（本会话） | 中位 **329K** tok | 中位 40.2s，miss 步 100~176s |

同一端点、同一机器、同一项目：OpenCode 快是因为**它从不发大 prompt**（无 230 条工具结果堆积），且小 prompt 天然不易触发整段 miss。它同样有 61s/138.6s 的离群值，与该端点的不稳定性一致。

## 五、路由核查（v3 结论保留）

- `Find-NetRoute` 显示含 agnes 在内的全部公网流量走 `utun12`（sing-tun 全局隧道），traceroute 任意目标均"1 跳 <1ms"；
- 但同隧道 RTT 对照：agnes tcp 26.5ms/tls 73.8ms，为全场最快（deepseek 48/87ms；openrouter 190ms；anthropic 944ms）→ **未出国**；
- 上传隔离实验：1MB body 仅 0.34s（~3MB/s），与 deepseek 对照持平 → 链路不构成瓶颈；
- DNS 三方解析一致、无 hosts 覆盖、无代理设置、IPv6 未参与。
- **判定：10.7s/67s 级延迟与路由无关。** 遗留：未找到 sing-tun 进程与配置，无法核对其分流规则。

## 六、建议

1. **治本：压缩进入上下文的工具结果**（占 prompt 77%）
   - 大文件用分页/片段读取，检索优先 `grep` 而非整文件读入；单条工具结果设上限（如 ≤8K token）；
   - 这样即使发生整段 miss，重算成本也从 150s 降到 20~40s 量级。
2. **保持前缀稳定**：避免长跑会话中途 compaction；宁可新开会话（干净前缀 + 小上下文），也别让上下文涨到 30 万+。
3. **大上下文任务改用 doubao / minimax**（doubao 实测 38 万 token/步 TTFT 仅 4.6s，缓存对间隔不敏感）。
4. **向 Agnes AI 反馈**：
   - 未缓存预填充 ~2.2K tok/s（命中时极快，说明缓存有效，但 34% 的步整段未命中且无法用间隔/剪枝解释）；
   - 流式请求 HTTP 500 / stream idle timeout；
   - 解码 47 tok/s（榜单 252.7）。
5. **判读口径**：以 `ttftMs` 墙钟为准，并区分"命中步 / miss 步"；单看 `cacheReadTokens` 会高估缓存收益。
